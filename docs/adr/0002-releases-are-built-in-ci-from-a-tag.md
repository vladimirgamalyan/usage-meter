# 0002. Releases are built in CI from a tag

- Status: Accepted
- Date: 2026-08-06

## Context

The app was distributed only as source: everyone who wanted it had to install
the MSVC toolchain and run `cargo build --release`. A published binary needs a
repeatable way to be produced and a place to live, and it needs to be clear
which commit any given binary came from.

## Decision

A GitHub Actions workflow (`.github/workflows/release.yml`) triggers on tags
matching `v*`, builds on `windows-latest` and publishes a GitHub release with
the resulting executable attached as
`usage-meter-<tag>-x86_64-windows.exe`. Release notes are generated by
`gh release create --generate-notes`, so the tag is the single input: pushing it
is the whole release procedure.

Windows is the only job. The binary is a native Win32 application (Credential
Manager, SChannel, `wsl.exe`, the window menu), so there is nothing to build for
another platform.

The executable is published on its own, without an installer or an archive: it
is a single ~450 KB file with no bundled dependencies, and settings live in
`%APPDATA%`.

## Consequences

- A release is reproducible from a tag by anyone with push rights, and the
  binary is traceable to the commit the tag points at.
- Release binaries are built by the runner's Rust toolchain, not a pinned one,
  so a toolchain regression would show up as a failed or changed release build.
- The version in `Cargo.toml` and the tag are maintained by hand and nothing
  checks that they agree.
- Windows SmartScreen will warn about the unsigned executable; code signing
  would need a certificate the project does not have.
